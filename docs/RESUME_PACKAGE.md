## 二、简历推荐版本（3 条）

### 版本 A｜AI 产品 / 产品经理方向（推荐）

- 主导从 0 到 1 设计并落地“二手文献引用助手”MVP，围绕人文社科真实痛点，将“二手转述 + 脚注 + 一手 PDF”转化为可回查的原文候选、页码、高亮证据和引用输出；完成需求定义、开源方案调研、UI 设计、真实案例评测与验收。
- 基于 PaperQA2、BGE 中文 embedding、pypdfium2 与 RapidOCR 复用成熟组件，设计文本层 / 扫描本双路径，并坚持“机器找证据、人做判断”的产品原则：多候选并列展示，不强制唯一答案，不伪造页码或版本。
- 设计 Weber / Plato 等真实学术材料评测与 6 套回归保护，定位并推动修复 PDF Unicode 兼容字符导致的原页定位失败；Fresh Case A 从 0 提升至 5 个可定位候选、Fresh Case B 恢复 PDF 110 页证据，最终全套回归通过。

### 版本 B｜更偏 AI 产品实习 / 模型应用

- 基于真实学术检索场景完成 AI 产品 MVP，从需求拆解、竞品 / 开源调研到端到端 Demo，支持非逐字转述的语义召回、原页定位、高亮与引用生成，并针对多候选、不确定性、版本冲突设计可解释交互。
- 采用本地 BGE embedding + PaperQA2 检索、pypdfium2 原页定位、RapidOCR 扫描本兜底；默认本地检索路径 0 付费模型调用，避免为“AI 感”堆叠无必要 Agent / reranker。
- 通过 Fresh Case 盲测发现“检索命中但证据回贴失败”问题，区分语义检索与 PDF 定位层后仅修复 Unicode NFKC 映射，真实案例恢复原页高亮且 6 套测试全绿。

### 版本 C｜更保守、避免技术误解

- 发起并主导“二手文献引用助手”AI 产品 MVP，负责用户需求定义、产品边界、交互设计、真实学术案例、验收标准和 AI Agent 协作管理；产品可从二手转述与脚注定位一手文献候选并提供原页证据。
- 通过 Reuse First 调研 PaperQA2、MinerU、Docling、RAGFlow 等方案，选择组合成熟开源组件而非从零开发 RAG；围绕“证据可回查”建立文本层 PDF / 扫描 PDF 两类路径。
- 组织真实案例盲测和回归测试，根据评测结果停止无收益的语义优化，将精力集中到 PDF 原页定位鲁棒性，完成一次可量化 Bug 修复与产品封箱。

## 四、30 秒项目介绍

> 我做了一个面向人文社科研究者的二手文献引用助手。用户给一段二手转述、脚注和一手 PDF，系统用本地语义检索把几百页缩小到几个候选，再把候选重新定位到 PDF 原页并高亮。项目最大的产品原则是“机器找证据，人做判断”，所以多个相关段落会并列展示，不会强行给唯一答案。我最后还用新的真实学术材料做盲测，发现并修复了 PDF Unicode 字形导致的原页定位问题，现在已经有完整 Demo 和回归测试。

---

## 五、2 分钟项目介绍

> 这个项目来自我自己的真实研究痛点。人文社科写作经常会引用二手文献，但真正写论文时需要回到一手文献确认原文、页码和上下文。普通聊天模型能解释观点，却很难给出可回查的原页证据，所以我把目标收敛成：给定二手转述、脚注和一手 PDF，返回一组值得人工核查的一手原文候选，并能回到原页高亮。
>
> 我没有从零写 RAG，而是先做 Research First，调研 PaperQA2、MinerU、Docling、RAGFlow 等方案，最后组合 PaperQA2、本地 BGE embedding、pypdfium2 和 RapidOCR。产品上我刻意把“检索排序”和“证据”分开：Top-1 不代表正确答案，多个合理候选就都给用户。
>
> 后期我冻结产品，用此前没参与调参的新真实材料盲测。Fresh Case A/B 都出现“语义检索已经命中，但原页高亮失败”的情况。诊断发现是 PDF 文本层 Unicode 兼容字符导致的定位问题，所以我没有继续调模型，而是只修定位层，加入 NFKC 归一化并保留到原字符坐标的映射。修复后 A 从 0 恢复到 5 个可定位候选，B 恢复到 PDF 110 页，全套 6 组测试通过。
>
> 我觉得这个项目最能说明的不是“我会调一个模型”，而是我能从真实问题出发，判断哪些功能值得做、怎么验证、什么时候应该停止继续优化，并把 AI Agent 组织成真正交付产品的工程能力。

## 六、高频面试追问

### Q1：为什么不用 ChatGPT 直接问？

答：

> 因为我的问题不是“韦伯怎么看”，而是“这句话到底对应哪一手原文、哪一页、上下文是什么”。聊天模型擅长生成解释，但学术核查要求原页可追溯。我做的是 evidence retrieval，不是再做一个聊天框。

### Q2：为什么不用一个大而全的 RAG 框架？

> Research First 后我发现没有必要。PaperQA2 已经能满足分块和检索，真正缺的是页级证据，所以我只补 pypdfium2 的定位与高亮层。成熟方案能复用的就复用，减少自研面和维护成本。

### Q3：这个项目到底用了 AI 在哪里？

> 核心 AI 能力是 semantic retrieval：把二手转述和一手 PDF 中的文本建立语义相似度，找到候选段落。脚注解析、页码、原页定位、高亮和状态机尽量做成确定性的工程逻辑，避免 AI 在证据层胡猜。

### Q4：准确率多少？

不要编一个百分比。

推荐答：

> 当前样本量不足以声称统计意义上的准确率，所以我没有宣传“95% 准确率”。我记录 Top-k、真实页定位、误候选、OCR 路径、延迟和失败类型。已知真实案例里，正确证据可能在 rank 5、rank 7，所以我没有把 Top-1 设计成自动答案。

### Q5：为什么后来不继续优化语义检索？

> 因为真实盲测证明当前召回已经能把用户带到正确区域，而真正阻塞产品可信度的是候选无法回贴 PDF 原页。如果这时候继续调 embedding 或 reranker，收益不如修证据链，而且会让项目从产品 MVP 变成检索算法研究。

### Q6：你遇到过最有价值的 Bug 是什么？

> Fresh A/B 中检索已经命中，但最终页面显示“没找到可靠段落”。我把问题拆开后发现不是语义检索，而是 PDF 文本层中肉眼一样、Unicode 编码不同的兼容字形导致原页匹配失败。最后只改定位层的 NFKC 规范化和坐标映射，不动检索，两个真实案例都恢复了原页证据。

### Q7：你本人会不会写代码？项目代码是不是 AI 写的？

建议如实回答：

> 我不是工程师背景，代码实现大量由 ChatGPT / Codex 等 Agent 协作完成。我负责的是问题定义、产品取舍、方案调研、Agent 任务设计、真实测试、Human Gate 和最终验收。我不会把 AI 生成的代码冒充成自己手写，但我能解释核心架构、为什么这么选，以及出现问题时应该改哪一层。这也是我想做 AI 产品经理的重要原因。

### Q8：如果继续做，下一步是什么？

> 不会先加功能。我会先观察真实用户使用。如果大量新案例都出现召回不全，再考虑 reranker / query expansion；如果主要问题是资料源，就做 source acquisition；如果只是 UI 使用成本，就改交互。下一步应该由真实失败模式决定，而不是由技术清单决定。

## 七、不要这样说

不要说：

- “我独立研发了一套 RAG 算法”
- “准确率达到 95%”
- “系统可以自动判断文献引用是否正确”
- “支持所有文献”
- “完全替代人工核查”
- “我训练了大模型”

这些都不符合项目事实，也会让技术面试官一追问就穿帮。

---

## 八、面试时最应该强调的 5 个点

1. **真实痛点，不是课程作业。**
2. **Reuse First，不为了开发而开发。**
3. **证据可追溯，比生成答案更重要。**
4. **真实盲测暴露 Bug，再定向修复。**
5. **知道什么时候停止优化，守住 MVP 边界。**
