# 作品集 Case Study｜二流文科生的二手文献引用助手

## 1. 项目定位

这是一个由真实研究痛点出发的 AI 产品 MVP：

> 给定二手文献中的引用/转述、脚注和一手 PDF，帮助研究者快速找到可能对应的一手原文，并保留页码、原页高亮、上下文和版本信息。

它不是“自动判真伪”的学术裁判，而是一套**证据发现 + 回查辅助工具**。

---

## 2. 我的角色

我在项目中承担的核心职责是：

- 提出真实问题与目标用户场景；
- 定义产品边界和最小可用结果；
- 决定哪些能力值得做、哪些不做；
- 组织开源方案调研与 Reuse First 决策；
- 设计真实案例评测与 Human Gate；
- 参与 UI 结构设计与多轮验收；
- 根据真实失败案例决定修什么、不修什么；
- 用 ChatGPT / Codex / GitHub 组织实现、测试、交接和长期事实源。

代码实现大量由 AI Agent 协作完成。这个项目展示的不是“我手写了多少 Python”，而是：**我能否把一个模糊的真实问题，转成可验证的产品目标，并把 AI 工程资源组织到最终可用结果上。**

---

## 3. 问题从哪里来

在人文社科写作中，二手文献往往会写成：

> “韦伯认为……”

但脚注可能只给：作者、篇名、外文页码或一个中文译本线索。

真正写论文时，用户需要回答的是：

1. 一手原文到底在哪里？
2. 中文译本怎么说？
3. 页码是什么？
4. 上下文有没有重要限定？
5. 二手作者是不是综合了多个一手段落？
6. 这个引用版本有没有冲突？

普通聊天模型可以“解释观点”，但很难把答案稳定钉回 PDF 原页。

因此 MVP 的唯一目标被收敛为：

> **把一份真实学术 PDF 缩小到一组值得人工核查的原文候选，并提供原页证据。**

---

## 4. Research First：为什么没有从零写 RAG

项目第一阶段先调查现成轮子，而不是先写代码。

重点比较过：

- PaperQA2
- MinerU
- RAGFlow
- Docling
- Marker
- PaddleOCR / PP-StructureV3
- RapidOCR
- 其他 citation / evidence retrieval 项目

最终选择了“组合成熟组件”的路线：

- PaperQA2：负责文档分块和检索入口；
- BGE 中文 embedding：负责本地语义召回；
- pypdfium2：负责页级文本与字符坐标；
- Pillow：负责高亮图像；
- RapidOCR：只作为扫描本兜底。

关键决策：**不追求一个大而全的 RAG 框架，而是优先保证‘候选文本 → 原页证据’这条链不断。**

---

## 5. 产品设计原则

### 原则 A｜检索分数不是证据

一个候选排 Top-1，不代表它就是学术上的正确答案。

真实评测里：

- Weber Golden 的正确证据在 rank 5；
- Plato 扫描本的真实区域在 rank 7。

因此 UI 不显示“AI 已经替你选好了”，而是保留候选并让用户切换。

### 原则 B｜多段相关就都给

Fresh A / B 都证明：一个二手段落可能综合多个一手位置。

所以最终产品规则是：

> 多个段落都合理相关时，全部呈现；系统不替用户决定哪些最终成立，也不替用户完成解释和评价。

### 原则 C｜找不到也是合法结果

系统明确区分：

- 已找到可回查证据；
- 多个可能段落；
- 暂未找到可靠对应证据；
- 当前资料不足。

宁可失败，也不编页码、高亮或版本。

---

## 6. UI 为什么这样设计

结果页经历多轮手绘草图与真实页面迭代，最终形成桌面端双工作区：

### 左侧

- 来源 PDF；
- 书目信息；
- 独立黄色版本冲突卡；
- 候选段落列表；
- 当前查看状态。

### 右侧

- 原页证据；
- 原文；
- 脚注 / 参考文献；
- 独立滚动区域。

UI 的核心不是“更炫”，而是减少解释性废话，让用户直接进入证据。

---

## 7. 真实评测怎么做

开发完成后没有继续无限调参，而是冻结产品，用此前没参与调参的新材料做盲测。

评测覆盖：

- 文本层 PDF；
- 1800 页超长 PDF；
- 跨页候选；
- 459 页纯扫描 PDF；
- 非逐字转述；
- 多段综合转述；
- 版本冲突；
- Unicode 文本层异常。

### 代表结果

| 案例 | 关键结果 |
| --- | --- |
| Weber Golden | 正确证据进入候选并回到原页；版本冲突保留 |
| C04 | 10/10 保存候选完成唯一原页定位；跨页高亮通过 |
| Plato OCR | 真实区域 rank 7；扫描本可回到原页 |
| Fresh A | 人工 gold = PDF 127–131 + 140–141；修复后 5 个候选可定位 |
| Fresh B | Top-1 即进入高相关区域；人工 gold = PDF 43–44 + 107–111 |

M3 之后决定：**当前语义检索已经够用，不再为了指标继续堆模型。**

## 8. 最有价值的一次 Bug

Fresh A / B 出现同一个现象：

> 检索明明已经抓到相关段落，但最终页面却说没有可靠对应证据。

诊断发现：PDF 文本层包含肉眼相同、编码不同的 Unicode 兼容字形。

这意味着：

- 检索层没坏；
- 真正坏的是候选文本重新定位回 PDF 原页的那一层。

修复策略没有扩大成“做一个更复杂的模糊匹配器”，而是最小化处理：

- 增加 Unicode NFKC 规范化；
- 逐字符保留到原 PDF entry 的坐标映射；
- 匹配不唯一仍返回 ambiguous；
- 不允许为了高亮成功而猜页码。

结果：

- Fresh A：0 → 5 个可定位候选，7 张高亮；
- Fresh B：0 → 1 个可定位候选，成功回到 PDF 110；
- 六套回归全部通过。

这次修复体现的产品判断是：**先修“证据链断裂”，而不是先追求更高的语义分数。**

---

## 9. 最终 MVP 能做什么

可以：

- 接收二手引文 / 转述 + 脚注；
- 使用本地或定向找到的一手 PDF；
- 文本层 PDF 本地语义检索；
- 扫描 PDF 走 RapidOCR；
- 返回多个候选；
- 回到原页并高亮；
- 显示版本冲突；
- 输出可复制引用；
- 明确暴露不确定性。

不做：

- 自动判定唯一正确答案；
- 自动评价作者是否曲解；
- 保证召回全部相关段落；
- 自动论文写作；
- 为了展示“AI 感”而堆多 Agent。

## 11. 我从这个项目学到什么

### 产品层

- 真实问题比“AI 功能列表”更重要；
- 如果产品输出不能被用户核查，再聪明的回答也不够；
- “不替用户做判断”本身可以是一条重要产品原则；
- 到达 MVP 标准后，继续优化未必比停止更正确。

### AI 协作层

- 复杂项目需要明确事实源，GitHub 比聊天记忆可靠；
- AI Agent 适合执行、测试和回归，但产品边界、Human Gate 和真实验收必须单独管理；
- Reuse First 能显著减少不必要开发；
- “让 AI 自己写代码”不等于“让 AI 自己决定产品”。

---

## 12. 最终一句话

> 我不是为了做一个 RAG Demo，而是把自己真实遇到的学术核查痛点，做成了一个能跑、能回到原页、能暴露不确定性的产品 MVP。
